# LLM 태깅 규칙 문서 (v1, 2026-10-11)

> 목적: 지금까지 7c(Claude)가 손으로 해 온 태그 후보 작업을 다른 LLM(로컬 모델 포함)이 같은 규칙으로 따라 하게 한다. 7c가 만들고 f2가 검수한 결과(`data/tag_candidates_*.tsv`와 시트 '태그 기록 (Claude)')가 나중에 모델 성능을 재는 **정답지**가 된다. 그래서 규칙은 "무엇을 하라"뿐 아니라 "무엇을 하지 말라"까지 적는다.
> 이 문서의 출력은 어디까지나 **후보**다. 시트에 넣기 전에 사람이 검수한다.

## 0. 한눈에

| 일 | `kind` | 입력 | 출력 | 정답지(사람 검수본) |
|---|---|---|---|---|
| 작품 테마 | `work_theme` | 공연 소개 글 또는 소개 이미지 | 사전의 `작품 · …` 태그 + 근거 한 줄 | `data/tag_candidates_works_2026-10-11.tsv` (시범 10편, 35행) |
| 배우 특징 | `actor_trait` | 설문 응답·관객 후기·기사의 글 | 사전의 `배우 · …` / `배우 조합` 태그 + 근거 한 줄 | `data/tag_candidates_survey2c/2d_*.tsv` 외 기존 후보 파일 |

모델이 하는 일은 항상 같다: **입력 글에 있는 말만 근거로, 사전에 있는 확정 태그를 골라, 내 말로 한 줄 근거를 쓰고, 확신을 표시한다.** 못 고르면 비워 두고 이유를 남긴다. 억지로 채우지 않는다.

## 1. 입출력 형식 (JSON, 스키마 `pickle-tagging/1`)

필드 이름은 영어 snake_case, 값은 한국어다. 한 입력 = JSON 한 건, 한 출력 = JSON 한 건(JSON Lines로 묶어도 된다).

### 1-1. 입력

공통 필드

| 필드 | 필수 | 설명 |
|---|---|---|
| `schema` | ○ | 항상 `"pickle-tagging/1"` |
| `kind` | ○ | `"work_theme"` 또는 `"actor_trait"` |
| `id` | ○ | 입력 한 건의 고유 id. 출력의 `input_id`로 돌아온다 |
| `allowed_tags` | ○ | 쓸 수 있는 태그 목록 `[{tag, group, meaning, phrases[]}]`. `group`이 `작품 · …`(work_theme) 또는 `배우 · …`·`배우 조합`(actor_trait)인 **확정 태그만** 준다 |
| `kopis_url` | 선택 | KOPIS 공연 상세 주소. work_theme의 근거 링크 기본값 |
| `intro_images` | 선택 | 소개 이미지 주소 목록. 글이 비었을 때만 쓴다(1-4) |
| `existing_tags` | 선택 | 이미 있는 태그 `[{work, actor, tag, source}]`. 같은 (대상, 태그, 출처)는 다시 내지 않는다 |

`work_theme` 추가 필드

| 필드 | 필수 | 설명 |
|---|---|---|
| `title` | ○ | currentShows의 `title` **표기 그대로**(85가 이 이름으로 공연과 잇는다) |
| `venue`, `area` | | 공연장, `"대학로"` 또는 `"대학로 외"`. 판단에는 쓰지 않는다(표기용) |
| `genre`, `age`, `runtime` | | KOPIS 값 |
| `synopsis` | | 근거 글(KOPIS `sty`, 제작사 공식 소개 등). 비었으면 `""` |
| `synopsis_source` | synopsis가 있으면 ○ | `{level: "제작진·공식" \| "전문매체·언론", url}` |

`actor_trait` 추가 필드

| 필드 | 필수 | 설명 |
|---|---|---|
| `source` | ○ | `{type, level, url, tag}` — `type`은 `"2차 설문"`·`"관객 후기"`·`"전문매체"` 등, `level`은 `"설문"`·`"일반 관객 후기"`·`"전문매체·언론"`, `tag`는 근거 문장 끝에 붙일 표시(예: `"2차 설문 #c09de5f8"`, 블로그는 도메인) |
| `context` | ○ | `{actor, work, season, role, partner}`. 모르는 칸은 `""`. 배우 선호 질문처럼 작품을 말하지 않는 글은 `work: "배우 전반"` |
| `segments` | ○ | `[{label, text}]`. 설문은 `"배우 선호 이유"`·`"배역 선호 이유"`·`"공통 취향 한 문장"`처럼 질문별로 나눠 준다. 후기는 `"본문"` 하나여도 된다 |

### 1-2. 출력

```json
{
  "schema": "pickle-tagging/1",
  "kind": "work_theme",
  "input_id": "PF297912",
  "rows": [ /* Row, 아래 */ ],
  "skipped": [ {"text": "건너뛴 표현(짧게)", "reason": "코드"} ],
  "dict_proposals": [ {"theme": "사전에 없는 테마", "reason": "왜 필요한지 한 줄"} ]
}
```

`rows`가 비어도 된다. 그때는 `skipped`에 이유를 꼭 남긴다.

**Row (work_theme)**

| 필드 | 값 |
|---|---|
| `work` | 입력 `title` 그대로 |
| `tag` | `allowed_tags`의 `tag` |
| `confidence` | `"높음"` \| `"보통"` |
| `status` | `"확정"` \| `"검수 필요"` (confidence와 짝: 높음→확정, 보통→검수 필요) |
| `evidence` | 내 말로 쓴 한 문장 |
| `evidence_level` | 입력 `synopsis_source.level`과 같은 값. 글이 없고 이미지로 판단했으면 KOPIS 소개 이미지는 `"제작진·공식"` |
| `source_url` | 근거 링크(필수). 기본값은 입력 `kopis_url` |

**Row (actor_trait)**

| 필드 | 값 |
|---|---|
| `target` | `"배우"` \| `"조합"` |
| `work` | 작품명 또는 `"배우 전반"` |
| `season` | 관람 연도(예 `"2025"`), 모르면 `""` |
| `role` | 배역. 1인 2역은 `"엘렌 / 에바"`처럼 슬래시로 |
| `actor` | 배우(조합이면 기준 배우) |
| `partner` | 조합일 때만 상대 배우, 배우 행이면 `""` |
| `tag` | `allowed_tags`의 `tag` |
| `scope` | `"작품 전체"`(기본) \| `"특정 넘버"` \| `"특정 회차"` — 글이 넘버·회차를 콕 집었을 때만 뒤의 둘 |
| `interpretation_diff` | `"없음"`(배우 행 기본) \| `"있음"`(같은 배역의 다른 배우와 해석이 다르다는 말이 있을 때) \| `"해당 없음"`(조합 행) |
| `confidence` | `"높음"` \| `"보통"` \| `"낮음"` |
| `status` | `"확정"` \| `"검수 필요"` \| `"보류"` (높음→확정, 보통→검수 필요, 낮음→보류) |
| `evidence` | 내 말로 쓴 한 문장 + 끝에 입력 `source.tag`를 괄호로 |

`대분류`·`하위 영역`·`연결 취향축`은 모델이 쓰지 않는다. 변환기가 사전(`data/tag_dict_2026-10-06.tsv`)에서 채운다. `기록일`·`기록자`·`근거 수준`·`출처 종류`·`출처 링크`도 변환기가 채운다.

**`skipped.reason` 코드**: `본인 취향` · `성별 선호` · `외모` · `나이` · `친분` · `우열 표현` · `부정 서술` · `사전에 없음` · `근거 불충분` · `다른 사람 이야기` · `중복` · `판단 불가`

### 1-3. 검사기가 확인할 수 있는 규칙

| 규칙 | 어기면 |
|---|---|
| `tag`가 입력 `allowed_tags`에 있다. work_theme은 `group`이 `작품 · …`, actor_trait는 `배우 · …`/`배우 조합` | 오류 |
| `confidence`↔`status` 짝이 맞다(작품 테마는 `낮음`·`보류` 없음) | 오류 |
| `evidence`가 비어 있지 않고 한 문장(마침표·물음표 합쳐 1개 이하)이며 100자 이하 | 오류 |
| `evidence`와 입력 글(`synopsis`/`segments.text`)이 **연속 3어절 이상** 같다 | 경고(원문 복사 의심) |
| 근거에 **금지어**가 있다(1-5) | 오류 |
| work_theme: `source_url`이 있고 `https://`로 시작, `evidence_level`이 입력 `synopsis_source.level`과 같다(이미지 판단이면 `제작진·공식`) | 오류 |
| actor_trait: `target`이 조합이면 `partner`가 있고 `interpretation_diff`는 `해당 없음`, 배우면 `partner`가 빈 값 | 오류 |
| actor_trait: `evidence`가 입력 `source.tag`로 끝난다 | 오류 |
| actor_trait: `work`가 `배우 전반`이면 `role`·`season`이 빈 값 | 경고 |
| 같은 (`work`/`actor`, `tag`)가 한 출력에 두 번 | 경고 |
| `existing_tags`에 이미 있는 (대상, 태그, 출처) | 경고(중복) |
| 한 입력에서 태그가 8개를 넘는다 | 경고(억지로 채운 흔적) |

### 1-4. 근거가 비었을 때 (`synopsis`·`intro_images`)

1. `synopsis`가 있으면 그 글로만 판단한다. 이미지는 보지 않는다.
2. `synopsis`가 비고 `intro_images`가 있으면 이미지를 읽어 판단한다. 이때 **이미지 속 관객 후기·평점 말풍선·수상 문구·캐스팅 사진 설명은 근거로 쓰지 않는다.** 공연 소개·줄거리·관람 포인트에 해당하는 공식 문구만 쓴다. 이미지는 판단할 때만 보고 저장하지 않는다.
3. 둘 다 비어 있으면 `rows: []`, `skipped: [{"text": "", "reason": "판단 불가"}]`로 낸다. 제목·장르·공연장·관람 연령만으로 테마를 짐작하지 않는다.
4. 글이 있어도 테마를 정할 만큼 구체적이지 않으면 `skipped`에 `근거 불충분`.

### 1-5. 금지어(근거 문장에 쓰지 않는다)

actor_trait 근거(배우 관련): 외모·얼굴·잘생·예쁘·미남·미녀·비주얼·훈남·섹시·몸매·체격·피지컬·키가·나이·연하·연상·동갑·친분·친구 사이·절친·사귀·열애·부부 같은 외모·나이·친분 말, 그리고 우열 말(최고·최상·제일·1위·1등·순위·더 좋·덜 좋·차원이 다르).
work_theme 근거는 줄거리 설명이라 위 단어가 등장인물 설명으로 나올 수 있다. 그래도 배우 이야기로 쓰지 않는다.

## 2. 공통 판단 규칙 (두 일 모두)

1. **사전 태그만.** `allowed_tags`에 없는 말은 태그로 만들지 않는다. 꼭 필요한 테마는 `dict_proposals`에 적는다.
2. **입력 글에 있는 말만 근거.** 짐작·배경지식·제목 연상으로 태그를 만들지 않는다. 사전의 "이런 표현이면 이 태그" 예시 단어(`phrases`)를 **근거에 보태지 않는다**(글에 없는 말을 글에 있는 것처럼 쓰게 된다).
3. **원문 금지.** 근거는 뜻만 가져와 내 말로 풀어 쓴다. 따옴표로 인용하지 않는다. 원문의 핵심 형용사·명사('서늘한', '공포' 같은 것)를 그대로 쓰지 말고 다른 말로 바꾼다. 태그 이름 자체(성량 등)는 그대로 써도 된다. 연속 3어절 이상 같으면 다시 쓴다.
4. **근거는 단독으로 읽혀야 한다.** "같은 글." 같은 앞 행을 가리키는 말을 쓰지 않는다. 행마다 무엇을 두고 한 말인지를 다시 적는다.
5. **한 문장.** 문장 안에 판단 근거와 한계(확신이 보통인 이유)를 같이 쓴다.
6. **외모·나이·친분 표현은 태그로도 근거로도 쓰지 않는다**(1-5). 외모를 말하는 수식어가 섞여 있으면 그 수식어만 버리고, 나머지가 구체적이면 그 부분만 쓴다.
7. **우열·비교 표현을 남기지 않는다.** "A가 더 좋다", "차원이 다르다", 다른 배우와 견주는 말은 근거에 옮기지 않는다. 비교의 이유가 상대 배우의 아쉬운 점이면 태그를 만들지 않는다.
8. **부정 서술은 태그를 만들지 않는다.** "목소리가 거칠어서 별로" 같은 말은 `skipped`(`부정 서술`).
9. **중복을 피한다.** `existing_tags`에 같은 (대상, 태그, 출처)가 있으면 내지 않는다. 같은 블로그의 여러 글, 한 응답자의 여러 칸은 **한 사람의 의견**으로 센다(같은 태그를 여러 줄 만들어 부풀리지 않는다).
10. **모르면 비운다.** "목표 개수"는 없다. 근거 없는 행보다 빈 출력이 낫다.

### 확신 기준

| 확신 | 언제 | status |
|---|---|---|
| 높음 | 입력이 그 특성을 **구체적으로** 말하고, 사전 태그의 뜻과 곧바로 맞는다 | 확정 |
| 보통 | 태그와 맞아 보이지만 ① 한 단어 평가("좋다")·무엇이 좋은지 없음 ② 비유 표현 ③ 묶음 평가(두 명 이상을 한 문장으로) ④ 협찬·초대권 글 ⑤ 중심이 맞는지 불분명 ⑥ 해석이 갈림 ⑦ 1인 2역 안의 변화 | 검수 필요 |
| 낮음 | 맞을 수도 있다는 정도(배우 특징만 사용) | 보류 |

## 3. 작품 테마 (`work_theme`)

### 3-1. 판단 규칙

- 근거는 **공식 소개·줄거리·관람 포인트**(제작사·KOPIS·극장·언론 소개)만이다. **개인 후기로 작품 테마를 정하지 않는다.** 이미지 속 후기 말풍선·평점·수상도 근거가 아니다.
- 사전 `작품 · …` 태그만: 스토리 분위기(파멸·힐링·감동·유쾌·긴장감·묵직함), 넘버(락·팝·클래식 오페라·웅장한 앙상블·서정적 발라드·재즈·국악·주크박스), 볼거리(군무·무대 연출), 소재(로맨스·가족·성장·우정·연대·역사·실존 인물·판타지·초자연·예술·창작·사회·풍자).
- 소개가 **강조하는** 것만 태그로 한다. 줄거리 한 줄에 나온 소재를 전부 태그로 만들지 않는다. 한 작품당 보통 2~6개.
- 소재 태그는 이야기의 중심일 때만. 배경에 스치는 사랑·가족은 만들지 않는다.
- 넘버 태그는 음악 장르·구성을 **소개문이 직접 말할 때만**. 사진·제목·배우 이름으로 짐작하지 않는다. 장르가 여러 개 나열되면 가장 앞서거나 중심이라고 한 것만 `높음`, 나머지는 `보통`.
- 실존 인물·역사: 실제 사건·인물을 바탕으로 한다고 **소개가 밝힐 때** `높음`. 시대극이지만 소설 속 인물이면 `보통`.
- 결말을 소개가 말하지 않은 비극·파멸은 `보통`(`검수 필요`)으로.
- 공연 소개 이미지의 홍보 문구("최고의", "9.7점")는 공식 문구라도 **테마가 아니라 평가**라서 근거로 쓰지 않는다.
- `evidence_level`: 제작사·극장·KOPIS 소개면 `제작진·공식`, 언론 소개면 `전문매체·언론`.

### 3-2. 프롬프트 초안

```
너는 뮤지컬 공연 정보를 태깅하는 보조자다. 아래 [입력]의 소개 글(또는 소개 이미지)에 적힌 내용만 근거로,
[허용 태그]에서 이 작품의 테마에 맞는 태그를 고른다. 다른 말은 만들지 않는다.

규칙
1. 허용 태그에 있는 이름만 쓴다. 맞는 게 없으면 rows를 비우고 skipped에 이유를 쓴다.
2. 소개문이 "강조"하는 것만 고른다. 줄거리에 잠깐 나온 소재, 제목·장르·공연장에서 짐작한 것은 쓰지 않는다.
3. 이미지 속 관객 후기, 평점, 수상 문구는 근거가 아니다. 개인 후기로 테마를 정하지 않는다.
4. evidence는 소개문의 뜻을 내 말로 풀어 쓴 한 문장이다. 원문 구절(연속 3어절 이상)을 옮기지 않는다.
   허용 태그의 예시 표현을 근거에 보태지 않는다. 따옴표 인용 금지.
5. 확신이 높으면 confidence "높음"/status "확정". 장르 나열 중 일부, 소설 속 인물의 시대극, 결말 미언급 비극,
   소개가 직접 말하지 않았지만 맞아 보이는 경우는 "보통"/"검수 필요"로 하고, evidence 끝에 확신이 보통인 이유를 쓴다.
6. 사전에 없는데 꼭 필요한 테마가 있으면 dict_proposals에 theme와 이유만 적는다(태그로 쓰지 않는다).
7. 출력은 JSON 한 개만. 설명 문장을 붙이지 않는다.

출력 형식: {"schema":"pickle-tagging/1","kind":"work_theme","input_id":"…","rows":[{"work","tag","confidence","status",
"evidence","evidence_level","source_url"}],"skipped":[{"text","reason"}],"dict_proposals":[{"theme","reason"}]}

[입력]
{입력 JSON}
```

### 3-3. 좋은 예·나쁜 예

**좋은 예 1 — 소개가 강조하는 것을 근거와 함께 (곤 투모로우)**

```json
{"schema":"pickle-tagging/1","kind":"work_theme","input_id":"PF297912",
 "rows":[
  {"work":"곤 투모로우 [대학로]","tag":"역사·실존 인물","confidence":"높음","status":"확정",
   "evidence":"공식 소개가 갑신정변을 일으킨 혁명가 김옥균의 마지막 시간을 바탕으로 한다고 밝힌다",
   "evidence_level":"제작진·공식","source_url":"https://kopis.or.kr/por/db/pblprfr/pblprfrView.do?menuId=MNU_00020&mt20Id=PF297912"},
  {"work":"곤 투모로우 [대학로]","tag":"파멸","confidence":"보통","status":"검수 필요",
   "evidence":"혁명이 사흘 만에 무너지고 암살로 이어지는 줄거리지만 소개문이 비극적 결말을 강조하진 않아 확신 보통",
   "evidence_level":"제작진·공식","source_url":"https://kopis.or.kr/por/db/pblprfr/pblprfrView.do?menuId=MNU_00020&mt20Id=PF297912"}],
 "skipped":[{"text":"기사 후기 문구(이미지 속 리뷰 칸)","reason":"근거 불충분"}],"dict_proposals":[]}
```
좋은 이유: 소개가 밝힌 것(`높음`)과 줄거리만으로 짐작되는 것(`보통`)을 나눴고, 이미지 속 리뷰는 근거에서 뺐다.

**좋은 예 2 — 장르 나열에서 중심을 가려냄 (콰이어 오브 맨)**: 소개가 "팝, 록, 포크, 합창"을 나열 → `팝 넘버`는 `높음`(대중가요 히트곡으로 채운다고 밝힘), `락 넘버`는 `보통`("중심 장르인지 불분명"). 기존 히트곡을 엮었다고 밝혔으므로 `주크박스`는 `높음`.

**나쁜 예 1 — 원문 복사**
`"evidence": "코믹 한 스푼 올린 웃음 가득 뮤지컬"` → 소개 문구 그대로다(연속 3어절 이상 일치, 경고). 고치면: "소개문이 웃음 포인트가 많은 코믹한 구성을 내세운다".

**나쁜 예 2 — 사전 밖 태그, 짐작**
`"tag": "누아르"`, `"tag": "액션"` → 사전에 없다. 필요하면 `dict_proposals`에 적는다. 또 "제목이 '프리즌'이니 교도소 이야기"처럼 제목만으로 소재를 짐작하지 않는다.

**나쁜 예 3 — 후기로 테마 정함**
이미지 속 관객 후기("눈물 났어요")를 보고 `감동`을 `확정`으로 낸다 → 개인 후기는 작품 테마의 근거가 아니다. 소개 문구가 직접 말하지 않으면 만들지 않는다.

**나쁜 예 4 — 확신 표시가 어긋남**
소개가 사랑·집착·의심을 함께 말하는데 `로맨스`를 `높음/확정`으로 낸다 → 중심이 로맨스인지 불분명하면 `보통/검수 필요`.

## 4. 배우 특징 (`actor_trait`)

### 4-1. 판단 규칙

**입력 글에서 쓰는 것**
- 설문: `배우 선호 이유`(작품 `배우 전반`), `배역 선호 이유`(작품·배역 행), `같은 배역 비교 이유`, `페어 선호 이유`(조합 행). 응답자 **본인의 취향을 말하는 칸(공통 취향 한 문장 등)은 배우 태그로 쓰지 않는다**(`본인 취향`). "여성 배우에게 끌린다" 같은 **성별 선호는 쓰지 않는다**(`성별 선호`).
- 후기·기사: 배우 이름과 특성이 붙은 문장만. 줄거리 소개·캐스팅 나열·협찬 문구·인물 이야기(가십)는 쓰지 않는다.
- 취향과 먼 페어(맞지 않았다는 이유)는 태그를 만들지 않는다.

**대상 구분**
- `target: "배우"`: 한 배우의 특성. 설문 배우 선호 칸은 `work: "배우 전반"`, 배역 칸은 작품·배역을 적는다.
- `target: "조합"`: 두 배우가 함께 한 장면·호흡을 말할 때(페어 선호 이유). `actor`는 기준 배우, `partner`는 상대, `interpretation_diff: "해당 없음"`. 조합 행의 `대비 시너지`는 "온도·성격의 대비"를 말한 경우(예: 차갑고 날 선 인물을 따뜻한 인물이 감싼다).
- 페어 이유에 상대 배우의 특성이 직접 적혀 있어도 그 배우 행은 **검수 필요**로만 낸다(규칙상 조합 행만 확정).

**태그별 조심할 것**
- 음색(맑음·부드러움·허스키·묵직한 음색): 응답에 해당 말이 있을 때만. 사전 예시 표현을 짐작으로 붙이지 않는다('미성'만 있는데 '높고 여린'을 붙이지 않는다).
- 표정·시선 디테일: 눈빛·표정·시선을 **구체적으로** 말하면 `높음`. "눈빛이 좋다"만이면 `보통`.
- 자세·동작 디테일: "몸짓이 좋다"처럼 무엇이 좋은지 없으면 `보통`.
- 코믹 연기: 웃음을 이끈다는 말만 있고 어떤 장면인지 없으면 `보통`.
- 외모 수식어가 붙은 칭찬(예: "○○한 몸짓")은 그 수식어를 버리고, 남은 말이 구체적이지 않으면 `보통`으로.

**1인 2역·역할 때문에 바뀐 목소리**
- 한 배우가 두 배역을 맡거나 변신 장면이 있는 작품에서 **그 역을 위해 바꾼 목소리·분위기**를 음색 태그로 배우 전체에 넣지 않는다. 낸다면 배역 행(`role`에 `엘렌 / 에바`처럼)에 `검수 필요`로, 근거에 "배역 안의 변화"임을 적는다.
- 눈빛·표정·동작처럼 **연기 기술**은 이 제한을 받지 않는다(구체적이면 확정 가능).
- 같은 응답의 배우 전반 행(그 배우의 평소 목소리를 말한 칸)과 배역 행은 **각각 따로** 판단한다. 같은 태그가 두 행에 있어도 된다(범위가 다르다).

**동명이인·표기**
- `context.actor`는 입력 표기 그대로 쓴다. 활동명과 본명이 다르게 올라오는 배우는 `data/actor_aliases.tsv`(활동명·KOPIS/본명 표기·적용 공연)로 맞춘다. 같은 이름의 다른 사람일 수 있는 글(다른 작품·장르, 배우가 아닌 문맥)은 `검수 필요`로 하고 근거에 "동명이인 가능"을 적는다. 확신이 없으면 내지 않는다.

**시즌·공연장**
- `season`은 글이 말한 관람 연도. 모르면 `""`(추측하지 않는다).

**후기·기사 글의 근거 문장 형식**
- `YYYY년 관람 후기에서 ○○ 역의 … 점을 꼽았다 (도메인)` 처럼 연도·종류를 앞에 쓴다. 설문은 `… 꼽았다 (2차 설문 #앞8자리)`.
- 협찬·초대권 글, 두 명 이상을 한 문장으로 묶은 평, 비유 표현은 `검수 필요`로 하고 근거에 그 사실을 **먼저** 쓴다.
- 광고성·AI 템플릿형 글(문장이 일반적이고 배우 정보가 겹치는 SEO 글), 보도자료 같은 소개, 외모·가십 글은 쓰지 않는다.

### 4-2. 프롬프트 초안

```
너는 뮤지컬 배우의 특징을 태깅하는 보조자다. [입력]의 글(segments)에 적힌 말만 근거로, [허용 태그]에서 배우의 특징에 맞는 태그를 고른다.

규칙
1. 허용 태그에 있는 이름만 쓴다. 근거에 사전의 예시 표현을 보태지 않는다(글에 없는 말은 쓰지 않는다).
2. 쓰지 않는 것: 응답자 본인 취향 문장, 성별 선호, 외모·나이·친분을 말하는 표현, 다른 배우와 견주는 말(더 좋다, 차원이 다르다 등), 부정 서술.
   외모 수식어가 섞인 문장은 그 수식어만 버리고 남은 말이 구체적일 때만 쓴다.
3. evidence는 글의 뜻을 내 말로 쓴 한 문장이고 끝에 입력의 source.tag를 괄호로 붙인다. 원문 구절(연속 3어절 이상)을 옮기지 않고 따옴표로 인용하지 않는다.
   원문의 핵심 형용사를 그대로 쓰지 말고 다른 말로 바꾼다.
4. 확신: 구체적이고 태그 뜻에 곧바로 맞으면 "높음"/"확정". 한 단어 평가, 무엇이 좋은지 없음, 비유, 두 명 이상 묶음 평가, 협찬 글,
   1인 2역 안에서 바뀐 목소리·분위기는 "보통"/"검수 필요"(근거 문장에 이유를 쓴다). 맞을 수도 있는 정도면 "낮음"/"보류".
5. 배우를 말하는 칸은 work를 "배우 전반", 배역을 말하는 칸은 작품·배역을 쓴다. 1인 2역은 role을 "A / B"로 쓴다.
   두 배우의 호흡을 말하면 target "조합"(partner 필수, interpretation_diff "해당 없음").
6. existing_tags에 있는 (대상, 태그, 출처)는 내지 않는다. 같은 응답자·같은 블로그는 한 사람의 의견이다.
7. 낼 게 없으면 rows를 비우고 skipped에 text와 reason을 쓴다. 억지로 채우지 않는다.
8. 출력은 JSON 한 개만. 설명 문장을 붙이지 않는다.

출력 형식: {"schema":"pickle-tagging/1","kind":"actor_trait","input_id":"…","rows":[{"target","work","season","role","actor","partner","tag",
"scope","interpretation_diff","confidence","status","evidence"}],"skipped":[{"text","reason"}],"dict_proposals":[]}

[입력]
{입력 JSON}
```

### 4-3. 좋은 예·나쁜 예 (실제 사례, 입력은 요약)

**좋은 예 2 — 1인 2역의 목소리는 검수 필요 (박은태 앙리, 부드러움)**: "섬세하고 부드러운 느낌의 앙리"가 목소리인지 연기 분위기인지 불분명하고 배역 안에서 만든 변화라, `role: "앙리"`·`부드러움`·`보통/검수 필요`로 내고 근거에 "배우 전체 음색으로는 쓰지 않음"을 적는다.

**나쁜 예 1 — 외모 말과 사전 예시를 근거에 씀**
`"evidence": "그 섹시한 몸짓과 거칠고 갈라지는 질감의 목소리를 꼽았다"` → '섹시한'(외모 금지어), '거칠고 갈라지는 질감'은 응답에 없는 사전 예시 표현이다. 고치면 "목소리가 허스키하다는 점을 꼽았다".

**나쁜 예 2 — 본인 취향·성별 선호를 배우 태그로**
`{"actor":"장은아","tag":"허스키"}`를 "허스키한 여성 목소리에 끌린다"(공통 취향 문장)만 보고 `확정`으로 낸다 → 응답자 취향이지 배우의 특성이 아니다. 배우 선호 칸에 같은 말이 있을 때만 그 칸을 근거로 낸다.

**나쁜 예 3 — 1인 2역 안의 목소리를 배우 전체 음색으로**
홍광호 지킬(부드러움)·하이드(허스키)를 둘 다 `배우 전반`·`확정`으로 낸다 → 한 배우가 음색 축 양쪽에 놓여 '이 배우를 좋아하는 사람' 매칭이 깨진다. 역할 때문에 바꾼 목소리는 배역 행·`검수 필요`.

**나쁜 예 4 — 우열·비교를 근거에**
`"evidence": "다른 배우보다 고음이 더 낫다고 적었다"` → 비교 표현이다. 비교의 이유가 상대의 아쉬운 점이면 태그를 만들지 않고, 배우 본인의 특성만 말하면 그 특성만 쓴다.

## 5. 변환·검수 흐름(참고)

1. 입력 생성기(85) → 모델 → 출력 JSON → 검사기(85: 1-3의 규칙) → 변환기(21열 TSV, 사전으로 대분류·하위 영역·연결 취향축 채움, 기록일·기록자·근거 수준·출처 종류·링크 채움).
2. 변환 전에 `tag_records`와 (링크+배우+태그) 중복을 대조한다.
3. 사람이 상태(확정/검수 필요/보류)를 확인하고 시트 '태그 기록 (Claude)'에 넣는다. 이 검수본이 정답지다. 모델 성능은 정답지와 (대상, 태그) 일치율·상태 일치율·금지어 위반 수로 잰다.
4. 모델이 만든 행이 정답지에 없으면 곧바로 오류는 아니다(근거가 더 있었을 수 있다). **정답지에 있는데 모델이 못 낸 행**(재현율)과 **금지어·사전 밖 태그·원문 복사**(위반)를 따로 본다.

## 6. 이번 시범(작품 테마 10편)에서 나온 사전 추가 제안

| 제안 | 나온 곳 | 이유 |
|---|---|---|
| `관객 참여`(작품 · 볼거리) | 콰이어 오브 맨(관객이 무대에 오르고 객석에 맥주·스낵이 나옴), 페인터즈 | 객석과 함께하는 구성이 공식 소개의 핵심인데 대응 태그가 없다 |
| `논버벌 퍼포먼스`(작품 · 볼거리) | 페인터즈, 난타류 | 대사 없이 미술·타악·춤으로 이끄는 공연은 `무대 연출`·`군무`로 잡히지 않는다 |
| `R&B·힙합 넘버`(작품 · 넘버) | 헬스키친 | 소개가 R&B·힙합 사운드를 내세우는데 `팝 넘버`로 묶기엔 불분명해 `보통`으로 둠 |
| `가족 관람`(작품 · 소재가 아니라 관객 대상 구분) | 페인터즈, 크리스마스 캐럴 | `가족`은 가족 이야기라는 소재라서, 온 가족이 보기 좋다는 대상 정보는 따로 필요 |

## 7. 열린 문제

- 로컬 LLM은 글만 읽을 수 있어서 KOPIS 소개 이미지(글자가 이미지에 들어 있는 경우가 대부분, 이번 시범 10편이 모두 그랬다)를 판단하려면 **이미지에서 글자를 먼저 뽑는 단계(OCR 등)**가 따로 필요하다. 그 단계의 출력은 `synopsis`로 넣되, 후기·평점 말풍선·수상 문구는 OCR 단계에서 걸러야 한다.
- `confidence` 기준(구체성·비유·묶음 평가)은 사람 눈에는 분명하지만 모델이 같은 선을 긋는지는 정답지로 재 보아야 안다. 첫 비교에서 `보통` 행의 재현율을 따로 본다.
